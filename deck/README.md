# First Mate — Deck Edition

A bespoke Steam Deck build of First Mate for Boat Hackathon Demo Day
(Sat Nov 21, 1–5pm PT, Pier 9). Same proven engine, new fullscreen Deck UI.

**What it does:** Tap a sample crew (or paste a team chat) → get a Ship Log
(actions, decisions, shared links, short summary) plus an **All Accesses**
panel that lists every access the run made — and the ones it did not make,
with reasons. No typing required for the demo.

## Design principles

- **The product speaks for itself.** No oversell. The Deck home page
  carries an "Under the hood" panel of facts the app computes about
  itself — archive size and dates, run cost, dependency count — and a
  claim appears only where the code can prove it.
- **Agent-readable by default.** `GET /llms.txt` states the machine
  contract in plain text and `GET /agent.json` serves the same as a
  JSON manifest, so an agent can file a chat (`POST /api/ship-log`)
  and read the result back (`GET /api/latest`) without scraping a
  screen. Feedback from agents is a first-class input, not an
  afterthought.
- **Persistent state.** Every run is archived on disk in
  `data/ship-logs/` (markdown + JSON metadata + a check-off sidecar)
  and survives restarts; the home panel reports the real archive
  count with its oldest and newest entries, computed live.
- **Honest limits.** Local summaries are extractive, there are no
  accounts, offline links are labelled "Not fetched", and a local run
  costs $0.00 with no keys — stated in the UI, in `/llms.txt`, and in
  every run's All Accesses record.

## v2 — No typing on the Deck (the demo flow)

Pasting text with a gamepad is miserable, so v2 splits the job by device:

- **Phone = capture.** The Deck home screen shows a big **QR code**
  (`/qr.png`, encoding `http://<deck-lan-ip>:<port>/phone` — the LAN IP
  is detected server-side). Anyone scans it, pastes their team chat on
  the **phone**, and submits from there.
- **Deck = bridge display + offline brain.** The Ship Log is built and
  stored on the Deck, and the Deck home page has a **live panel** that
  polls `/api/latest` every 5 seconds — when a phone submission lands,
  the new Ship Log's actions/decisions appear on the big screen with a
  gold flash. Judges *see* the phone run arrive on the Deck.
- **Watch = glance + check off.** The watch shows the latest Ship Log's
  next actions; tapping one (on watch, phone, or the Deck live panel)
  checks it off everywhere via `POST /api/actions/done` — done actions
  render ✅ struck-through on all three surfaces, persisted on the Deck
  in a `-done.json` sidecar next to the log.

### v2 API (JSON, same server)

- `POST /api/ship-log` — body `{"chat": "...", "source": "Phone"}` →
  builds + saves a Ship Log, returns `{run_id, file, counts, actions,
  decisions, done}`. Empty/missing chat → `400 {"error": ...}`.
- `POST /api/actions/done` — body `{"index": 0}` (latest run) or
  `{"run_id": "...", "index": 0}` → toggles that action's done state,
  returns the full `done` array. Out-of-range → 400, unknown run → 404.
- `GET /api/latest` — latest Ship Log summary, now including
  `"decisions"` and `"done": [true/false per action]`.
- `GET /qr.png` — pairing QR PNG. Generated by `first_mate/qrmini.py`,
  a **vendored single-file QR library** (qrcodegen by Project Nayuki,
  MIT — see the file header), so the Deck needs no pip install.

### Inbox auto-import

Drop any team chat as a `.txt` file into the **`inbox/`** folder next
to `deck.py` (USB stick, file share, scp…). A watcher thread in the
server runs it as a Ship Log (source label `Inbox drop: <filename>`),
saves it like any other run, and moves the file to `inbox/processed/`.
See `inbox/README.txt`.

## Launch on the Steam Deck

1. Switch the Deck to **Desktop Mode** (Power menu → Switch to Desktop).
2. Open a terminal / file manager in this folder (`first-mate-deck/`).
3. Run:
   ```bash
   chmod +x launch.sh
   ./launch.sh
   ```
   It starts the server, waits for `/health`, then opens
   `http://localhost:8000` in the default browser. Press **F11** in the
   browser for true fullscreen if it does not open fullscreen.
4. Alternative (no script): `python3 deck.py` then open
   `http://localhost:8000` yourself.
5. Later: in Steam, **Add a Non-Steam Game** → point it at `launch.sh`
   so it can be launched from Game Mode. Not required for the demo.

- Port: `FIRST_MATE_PORT` (default `8000`). Host binds `0.0.0.0`, so on
  the same WiFi another phone/laptop can open `http://<deck-ip>:8000/logs`
  to view/share saved Ship Logs.
- Requirements: Python 3.10+. **Stdlib only — no pip installs, no keys.**

## Screens

- **Home (`/`)** — v2 pairing panel (QR + phone URL) and a live
  latest-Ship-Log panel at the top; below, big one-tap buttons
  (1280×800, min 20px text) for: Demo Chat, Startup Product Team,
  Event Crew, Open Source Team. Paste-your-own-chat textarea is below,
  as a secondary option (last resort — the phone flow replaces it).
- **Result** — Ship Log in a large readable block + All Accesses panel.
- **Saved Logs (`/logs`)** — Sync list of every Ship Log saved on-device
  in `data/ship-logs/` (existing engine behaviour, archived by run id).
- **Status (`/status`, JSON)** — Real connectivity check.

## Online vs Offline — honest behaviour

- The status header on every page shows **ONLINE** or **OFFLINE**,
  privacy mode, and `Hosting: Steam Deck (on-device)`.
  Online/offline is **actually checked server-side**: `/status` attempts
  a short-timeout (2s) fetch to example.com / boat.dev and reports the
  result; it is cached for 10 seconds. It is never hard-coded.
- **Online:** links in a chat are read via the engine's existing live
  path — Context.dev if a key is configured, otherwise direct fetch —
  and labelled with the source actually used.
- **Offline:** the same engine fetch fails honestly and links are
  labelled **`Not fetched`** in the Ship Log, with the link kept for the
  team to open. Nothing is faked.
- **Privacy:** Default is `Local only` — the summary runs on-device, no
  team data leaves the Deck. `Private via NYTE` appears only if that
  optional route is fully configured (key + base URL + model), exactly
  as the engine reports it. Context.dev / NYTE / Boat VM use is **never
  claimed unless actually used** — see the All Accesses panel per run.

## Phone app (installable PWA)

The phone is a second surface of the **same Deck server** — not a copy.

1. Put the phone on the **same WiFi** as the Deck.
2. Open `http://<deck-ip>:8899/phone` in Chrome (Android) or Safari (iOS).
3. **Add to Home Screen** (Chrome: ⋮ menu → "Add to Home screen" /
   "Install app"; Safari: Share → "Add to Home Screen"). First Mate
   installs as a standalone app (name "First Mate", nautical icon)
   via `/manifest.webmanifest` + `/sw.js`.
4. What you get: status pill (online/offline, privacy, hosting),
   one-tap sample runs, paste-your-own-chat, and the saved Ship Logs
   list with tap-to-view — all in a phone-sized layout. Runs made from
   the phone render in the phone layout too.
5. The service worker caches only the app shell (`/`, `/phone`,
   manifest, icons). **Sync data is never cached**: `/status`,
   `/logs`, `/sample`, `/watch`, `/api/latest` and POST results are
   always fetched live from the Deck.

## Watch app (Galaxy Watch companion)

1. Put the Galaxy Watch on the **same WiFi** as the Deck.
2. Open `http://<deck-ip>:8899/watch` in **Samsung Internet** on the watch.
3. You get the **latest Ship Log only**, watch-sized: black background,
   28px+ text — the log's date, the top 5 "What to do next" actions as
   a big checklist, counts of decisions / links / actions, and a
   "🔄 Synced • <time>" line. The page auto-refreshes every 30 seconds.
   **v2:** done actions show ✅ struck-through, and **tapping an action
   on the watch checks it off** (same synced done state as phone/Deck).
4. `GET /api/latest` returns the same latest-log summary as JSON
   (title, date, actions, top 5, counts) for a future native app.
5. If no Ship Log exists yet, the watch honestly says "No Ship Logs
   yet — run one on Deck or phone."

## Sync — how Deck, phone and watch stay in step

There is exactly **one source of truth**: the First Mate server running
on the Steam Deck and its on-device store, `data/ship-logs/`. The Deck
UI, the phone app and the watch page are three surfaces of that same
server reading and writing that same store. A run made on **any**
surface is saved to the Deck and immediately appears on **all** of
them — the watch shows it as the latest log, the phone lists it under
Saved Ship Logs, the Deck's `/logs` list shows it too. Nothing is
copied between devices and no cloud account is involved; "synced"
means "same server, same files", and the UIs say exactly that.

**Honest limits:** the watch surface is a **web companion** today
(a page in Samsung Internet on the watch). A native Wear OS APK is a
separate build and is not claimed here. All surfaces require the same
WiFi network as the Deck (or the Deck itself); there is no internet
sync — by design, in Local only mode no team data leaves the Deck.

## Gamepad / keyboard

All buttons and links are real focusable elements: Tab moves in a
sensible order, **Enter/Space** activates, focus is shown with a thick
gold outline. On the Deck, the D-pad / right trackpad + A button work
through the browser the same way.

## Deck Mode v4 (2026-11-21)

The Deck UI is controller-first, because that is how a Steam Deck is
actually used in Gaming Mode:

- **No typing on the Deck, ever.** The home page has no paste form.
  Order: QR pair card → live Ship Log → sample crews → Under the Hood
  → "Why a persistent machine". Pasting lives on the phone.
- **Gamepad navigation** (`GAMEPAD_JS`, injected on Deck pages):
  D-pad / left stick / arrow keys move a thick gold focus ring between
  `.foci` elements (spatial nearest-neighbour); A / Enter / Space
  selects; B / Escape goes back; the menu button goes home.
- **Result pages are structured** — actions are big check-off rows
  (synced through the existing API), then decisions, links, and the
  All Accesses record in a collapsible panel. No raw markdown dump.
- **No stale UI, ever:** HTML is served `Cache-Control: no-store` and
  service worker `first-mate-v4` caches only the manifest + icons;
  navigations are network-only. Every relaunch shows the current build.
- **Friendly errors:** user-facing routes return styled HTML pages
  (an empty paste explains that pasting happens on the phone) — never
  bare text. API routes still return JSON.
- **Fifth sample — Agent Fleet Report** (`sample/agent-fleet-chat.txt`):
  named AI agents report work, blockers, and decisions to their human
  operator. Many agents, one human, one digest — the persistent-VM use
  case. The home panel and `/llms.txt` state the deployment story
  honestly: demo on-device; the package ships a Dockerfile + deploy
  guide for a persistent VM (Boat); it has not yet been run on Boat.
